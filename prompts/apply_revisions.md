# 첨삭 반영 절차 (정본)

`review.html`에서 내보낸 `revisions/rev_*.md`(첨삭 요청)를 원고에 반영하는 절차다.
Claude Code 대화에서 "revisions/rev_….md 반영해줘"라고 요청받았을 때와, `review_bridge.py`가 헤드리스로 부를 때 모두 이 문서를 따른다.

---

## 0. 대상 파일 정하기

- 사용자가 파일을 지정했으면 그 파일을 쓴다.
- "최근 첨삭 반영해줘"처럼 지정이 없으면 `revisions/`에서 **짝이 되는 `.applied.json`이 없는** `rev_*.md` 중 가장 최근 것을 고른다. 후보가 여러 개면 목록을 보여 주고 어느 것을 반영할지 묻는다.

## 1. 요청 파일 읽기

요청 파일을 **끝까지** 읽는다. 구조는 다음과 같다.

```
---
rev: rev_v003_260930-1520        ← 결과 파일 이름에 그대로 쓴다
base_version: 3                  ← 코멘트를 쓸 때 본 원고 버전 (versions/v003/)
scope: minimal | free            ← 수정 범위
sources:
  - path: manuscript/draft.md
    sha1: 1a2b3c4d5e             ← 빌드 시점 파일 바이트 sha1 앞 10자
---
## 전체 지시            ← block: ALL (문서 전체 대상)
## 블록별 수정 요청      ← 원고 순서대로 정렬되어 있다
## 위치를 잃은 요청      ← block: ORPHAN (작성 이후 원고가 바뀜)

### 3. [c-7f3a] 수정 · B012 · manuscript/draft.md:34-38 · Introduction
<!-- cid: c-7f3a | block: B012 | hash: … | file: … | lines: 34-38 | type: rewrite -->
**대상 구절**      (선택) 사용자가 드래그한 원고 문자 그대로
**요청**           사용자의 지시
**제안 문구**      (선택) 사용자가 정해 둔 대체 문장
**이전 에이전트 응답** (선택) 지난 라운드에 보류·부분 반영했을 때의 내 메모
<details> 원문 블록 </details>   ← 코멘트를 달 당시 블록 전체
```

## 2. 위치 찾기

1. 원고 파일의 sha1을 확인한다: `python -c "import hashlib,sys;print(hashlib.sha1(open(sys.argv[1],'rb').read()).hexdigest()[:10])" <파일>`
   - **같으면** 줄 번호(`lines`)를 그대로 믿어도 된다.
   - **다르면**(요청을 쓴 뒤 원고가 바뀜) 줄 번호는 참고만 하고, **원문 블록 → 대상 구절** 순으로 텍스트 검색해 위치를 찾는다.
2. 대상 구절은 원고 문자 그대로(마크업 포함)이므로 정확 일치 검색이 기본이다. 같은 구절이 여러 번 나오면 원문 블록 안에 있는 것을 고른다.
3. 위치를 끝내 찾지 못하면 고치지 않고 `skipped`로 보고한다(note에 이유).

## 3. 유형별 반영

| type | 라벨 | 할 일 |
|---|---|---|
| `rewrite` | 수정 | 대상 구절(없으면 블록)을 요청대로 고친다. 제안 문구가 있으면 **그 문구를 우선** 쓰고, 문법·마크업 때문에 바꿔야 했다면 무엇을 바꿨는지 note에 적는다. |
| `delete` | 삭제 | 대상 구절(없으면 블록)을 지운다. 앞뒤 문장이 어색해지면 연결어만 최소로 다듬는다. |
| `insert` | 추가 | 요청한 내용을 넣는다. 위치 지정이 없으면 대상 구절 바로 뒤, 구절이 없으면 블록 끝. |
| `style` | 표현 | 의미·주장·수치를 바꾸지 않고 표현만 다듬는다(문법, 간결성, 어휘, 톤). |
| `question` | 질문 | **원고를 고치지 않는다.** note에 답한다. 답에 따라 수정이 필요해 보이면 note에 제안만 적는다. status = `answered`. |
| `other` | 기타 | 요청 취지대로 처리한다. 뜻이 모호하면 고치지 않고 `skipped` + note에 확인 질문. |

**전체 지시(ALL)**: 문서 전체에 적용한다. 고친 위치를 note에 요약한다(예: "수동태 12곳 → 능동태, §2·§4 중심"). 블록별 요청과 충돌하면 **블록별 요청이 우선**이다.

**위치를 잃은 요청(ORPHAN)**: 원문 블록·대상 구절로 현재 위치를 찾아 반영하고, 찾지 못하면 `skipped`로 보고한다.

**이전 에이전트 응답이 있는 항목**: 사용자가 내 지난 메모를 보고 요청을 다시 쓴 것이다. 지난 메모에서 내가 제기한 문제를 이번 요청이 해소했는지 먼저 확인한다.

### 수정 범위 (scope)
- `minimal` (기본): 요청이 가리키는 문장·구절만 바꾼다. 같은 블록의 다른 문장, 다른 블록은 건드리지 않는다.
- `free`: 요청 취지 안에서 **그 블록 안의** 문장 순서·구조를 바꿔도 된다. 다른 블록은 여전히 건드리지 않는다.

## 4. 불변 조건 (항상)

- **요청하지 않은 곳은 건드리지 않는다.** 줄바꿈·들여쓰기·공백 정리, 다른 문장 다듬기도 하지 않는다. 그래야 다음 빌드의 변경 표시(diff)가 요청한 곳만 보여 준다.
- 인용(`\cite{}`, `[@key]`), 참조(`\ref{}`, `\label{}`), 수식, 수치, 고유명사는 요청이 없으면 그대로 둔다.
- 마크업이 깨지지 않게 한다(중괄호 짝, `\begin`/`\end` 짝, Markdown 강조 기호 짝, 코드 펜스).
- **없는 사실을 만들지 않는다.** 요청을 반영하려면 새 인용·실험 결과·수치가 필요한데 원고나 요청에 근거가 없으면, 자리표시(`[CITE?]`, `[N=?]`)를 넣거나 `partial`로 두고 note에 무엇이 필요한지 적는다.
- 원고의 언어(영어/한국어)와 기존 문체·용어 표기를 따른다.
- `review.html`, `versions/`, 요청 파일(`rev_*.md`)은 직접 수정하지 않는다.

## 5. 결과 기록

### 5-1. `revisions/<rev>.applied.json` (필수 · 스키마 고정)

```json
{
  "rev": "rev_v003_260930-1520",
  "applied_at": "2026-09-30T15:40:00+09:00",
  "summary": "요청 6건: 반영 4 · 부분 1 · 답변 1. Introduction 둘째 문단 주장 완화, Method 수식 설명 추가.",
  "items": [
    {"cid": "c-7f3a", "status": "applied",  "note": "'novel' 삭제, 차별점(토큰 단위 캐시 재사용)을 명시하는 문장으로 교체."},
    {"cid": "c-9b1c", "status": "partial",  "note": "문장은 줄였으나 비교 수치는 원고에 근거가 없어 [N=?] 자리표시를 넣음."},
    {"cid": "c-2d4e", "status": "answered", "note": "Eq. (2)의 λ는 §3.1에서 정의한 정규화 가중치다. 정의가 수식보다 뒤에 나오므로 순서를 바꾸는 것을 권한다."},
    {"cid": "c-5f6a", "status": "skipped",  "note": "대상 구절을 원고에서 찾지 못함 — 이미 삭제된 문장으로 보인다."}
  ]
}
```

- `status` ∈ `applied`(요청대로 반영) · `partial`(일부만 반영) · `skipped`(반영 안 함) · `answered`(질문 답변).
- **요청 파일의 모든 cid를 빠짐없이** 넣는다.
- `note`는 1~3문장. 무엇을 어떻게 바꿨는지(또는 왜 못 했는지)를 사실 위주로 쓴다. 사용자는 이 메모를 해당 블록 옆에서 본다.
- `applied_at`은 현재 시각(ISO 8601, 타임존 포함).

### 5-2. `revisions/CHANGELOG.md` (한 줄 덧붙이기)

```
- 2026-09-30 15:40 · rev_v003_260930-1520 · 반영 4 / 부분 1 / 보류 0 / 답변 1 · Introduction 주장 완화, Method 수식 설명 추가
```
파일이 없으면 `# 첨삭 반영 기록` 제목으로 새로 만든다. 건수는 기억에 의존하지 말고 **applied.json의 items를 status별로 세어** 쓴다(summary·CHANGELOG·REVISION_RESULT 모두 같은 수).

## 6. 다시 빌드

```bash
python build_review.py            # 킷 폴더에서 (다른 프로젝트면: python <킷>/build_review.py <프로젝트>)
```
출력이 `OK review.html · v004 (new snapshot) …`처럼 **새 버전**을 만들었는지 확인한다(원고를 하나도 안 고쳤다면 새 버전이 없는 것이 정상).

## 7. 보고

대화로 부른 경우: 요약 한 단락 + 보류·부분 반영 항목과 이유 + "review.html을 새로고침하면 변경 표시로 확인할 수 있다"는 안내.

브릿지(헤드리스)로 부른 경우: 마지막 줄에 정확히 한 줄 출력한다.
```
REVISION_RESULT: {"status":"ok","rev":"rev_v003_260930-1520","applied":4,"partial":1,"skipped":0,"answered":1}
```
